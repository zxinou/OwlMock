# OwlMock 产品化设计

## 目标与发布形态

OwlMock v1 面向个人求职者自部署，不建设集中式多租户 SaaS。默认交付顺序为 Railway 单服务部署，其次是 Docker Compose；两者复用同一个生产镜像、环境变量契约和持久化目录。

产品主链路是：创建一个具体目标岗位，完成 JD 分析，选择一份主简历生成匹配报告，再围绕相同上下文进行多轮文字或语音模拟面试。GitHub 分析继续作为可选增强能力，但不阻塞主链路发布。

已批准的主界面采用“岗位项目工作台”：登录后直接进入应用，不再先显示营销首页。视觉继续使用现有猫头鹰线稿、浅色/深色主题、深绿主色、金色强调和珊瑚色风险提示。概念稿保存在 `.superpowers/brainstorm/owlmock-productization-20260804/content/owlmock-workspace-concept.html`。

## 产品与交互设计

### 应用入口与导航

- `/login` 是唯一公开 UI；根路由根据会话跳转到登录页或 `/projects`。
- 全局导航包含岗位项目、简历库、面试记录、GitHub 分析、设置与诊断。
- `/projects` 展示进行中和已归档岗位；`/projects/new` 通过粘贴 JD 或上传 PNG/JPEG 创建项目。
- `/projects/:projectId` 是工作台，展示 JD、简历匹配、模拟面试三步状态，以及准备重点、岗位摘要和最近面试。
- 项目内报告和任务拥有独立 URL，刷新、后退和重新进入不会丢失进度。
- 原有分析与面试路由保留兼容跳转；无法归属项目的历史记录进入全局“未归档记录”，可手动关联到项目。

### 岗位项目生命周期

一个项目代表一个具体岗位，绑定一份当前 JD 和一份当前主简历，并可拥有多次简历匹配与多轮面试。项目创建后立即持久化为草稿；JD 分析完成后由结构化结果补全岗位名称、公司和地点，用户可以编辑这些字段。

工作台步骤由实际数据派生，不单独存一份容易失真的流程状态：

1. 存在已完成的当前 JD 分析时，岗位理解完成。
2. 存在当前简历及已完成的项目匹配时，材料适配完成并显示最新分数。
3. 存在项目面试时显示最近进度；完成总结后更新针对性准备建议。

项目使用归档而非级联删除。归档项目不删除共享简历、JD 报告、匹配报告、会话事件或记忆文件；历史库中的资产也不会因项目归档而消失。

### 文字与语音面试

文字和语音在 v1 中具有相同的稳定性承诺。创建会话时必须携带 `project_id`，后端从项目解析当前 JD、主简历、可选 GitHub 仓库和既有记忆，客户端不再拼装身份或上下文。

文字模式继续使用 POST + SSE；语音模式继续使用同源 WebSocket 和手动“开始回答/回答完毕”轮次。两种模式都必须支持：刷新后恢复、重复提交保护、超时回到可重试状态、断线后的明确恢复路径、幂等总结，以及项目内历史回放。语音还需在进入前完成浏览器权限、输入设备和实时模型连通性预检；录音中断时不得提交不完整回答。

## 后端与数据设计

### 单用户安全边界

实例只有一个逻辑所有者。数据库继续使用内部所有者 ID `default` 以兼容已有数据，但该值不再由浏览器传入：REST、SSE 和 WebSocket 都从服务端会话解析所有者身份，所有客户端 `user_id` 请求字段和查询参数被弃用并忽略或移除。

新增同源 Cookie 会话认证：

- `OWLMOCK_ADMIN_PASSWORD` 是必填部署变量，不在应用中存储或回显。
- 首次启动在持久卷生成签名密钥；也可用 `OWLMOCK_SESSION_SECRET` 显式覆盖。
- 登录成功写入 `HttpOnly`、`Secure`（HTTPS）、`SameSite=Strict` 的签名 Cookie；默认有效期 7 天。
- `/api/auth/session`、`/api/auth/login`、`/api/auth/logout` 管理会话；退出立即清除 Cookie。
- 除存活检查、最小就绪检查和登录接口外，所有 API、SSE 与 WebSocket 均先鉴权。WebSocket 在 `accept` 前验证 Cookie，失败使用 4401 关闭码。
- 修改类请求校验同源 `Origin`/`Host`；登录按来源 IP 做有限窗口退避，避免暴力尝试。
- 应用默认不开放跨域；反向代理只信任显式配置的转发头。

### 数据模型

新增 `job_projects`：

- `id`, `user_id`, `title`, `company`, `location`
- `current_jd_analysis_id`, `current_resume_id`
- `archived_at`, `created_at`, `updated_at`

为 `jd_analyses`、`resume_matches` 和 `sessions` 增加可空 `project_id` 外键与索引。新主链路创建的数据必须带项目；空值仅用于兼容既有记录和独立工具入口。项目工作台聚合当前 JD、当前简历、最新匹配、会话列表和派生步骤，不复制报告内容。

新增项目 API：

- `POST /api/projects` 创建草稿项目。
- `GET /api/projects` 分页列出进行中或归档项目。
- `GET /api/projects/{id}` 返回工作台聚合数据。
- `PATCH /api/projects/{id}` 编辑元数据、当前 JD/简历或归档状态。
- `POST /api/projects/{id}/jd-analyses` 复用现有异步 JD 管线并自动关联项目。
- `POST /api/projects/{id}/resume-matches` 使用项目当前 JD 和指定简历创建匹配任务，并更新当前简历。
- `POST /api/projects/{id}/sessions` 使用项目上下文创建文字或语音会话。

通用 JD、简历、匹配和会话读取接口继续保留，便于历史库和 GitHub 增强流程使用；所有详情、更新和删除都在服务端校验记录属于逻辑所有者。

### 迁移与兼容

用 Alembic 替代继续扩张的启动时 `ALTER TABLE`。引入一个经过验证的 legacy baseline：已有数据库若没有 `alembic_version`，启动器先校验旧表结构并标记 baseline，再执行新增项目关系的版本迁移；全新数据库直接升级到最新版本。

迁移不猜测旧数据之间的关系。已有 JD、匹配和面试记录保持 `project_id = NULL`，在全局历史中显示为“未归档”；用户可在界面中将其关联到任一项目。旧 `user_id=default` 数据原样保留。

### 持久化与备份

新增统一 `OWLMOCK_DATA_DIR`，默认开发值为 `./runtime`，生产值为 `/data`。SQLite、会话 JSONL、简历、JD 图片、记忆和仓库缓存都从该根目录派生；现有细粒度路径变量继续作为高级覆盖项。

SQLite 启用 foreign keys、WAL、busy timeout，并保持单 Uvicorn worker，避免当前进程内任务注册表与 SQLite 并发模型在多 worker 下产生分裂状态。启动时验证数据目录可写且有足够空间。

提供管理命令导出与恢复数据包。备份使用 SQLite 在线备份 API 获取一致数据库快照，并包含会话、简历、JD 上传和记忆；可重建的仓库缓存默认排除。恢复要求应用停止，先校验清单与版本，再原子替换数据目录。

### 配置、限额与诊断

模型密钥继续只通过 Railway/Docker 环境变量提供。认证后的 `/api/system/status` 和“设置与诊断”页显示能力状态、当前 provider/model、存储可写性、数据库版本、实时语音可用性和 GitHub 增强状态，但不返回任何密钥片段。

缺少管理员密码时应用以未就绪状态启动，只暴露最小诊断说明；缺少普通分析模型时允许登录但禁用 JD/匹配/文字面试；缺少实时模型时只禁用语音入口。每个禁用操作都显示可执行的环境变量修复说明。

生产配置包含上传大小、JD 长度、仓库文件数、并发分析数、语音会话时长和请求频率上限。超限在启动任务或读取大文件前失败，并返回稳定错误码；前端将错误码映射为用户可行动的提示。

## 前端与部署设计

### 前端架构

保留 Vue 3、Vite、Vue Router、Tailwind 和现有 CSS token。新增共享 AppShell、认证 store、项目 store、项目 API 客户端和按领域拆分的项目页面；不把工作台堆进单一页面组件。

API 客户端统一使用同源凭证，集中处理 401 跳转、结构化错误、上传请求和任务流。任何身份、模型密钥或数据根路径都不进入浏览器状态。任务状态以数据库响应为准，SSE 只用于及时更新。

实现必须忠实复现已批准概念：桌面固定侧栏、开放式工作区、三段流程栏、深绿准备重点、克制的圆角与阴影、完整暗色主题；窄屏收起侧栏并纵向排列流程。猫头鹰品牌资产复用现有 SVG/PNG，交互图标使用现有 Lucide Vue。

### 单镜像交付

根目录生产 Dockerfile 使用多阶段构建：Node 阶段生成 Vue 静态资源，uv/Python 阶段安装后端并复制静态资源。FastAPI 在 API 与 WebSocket 路由之后提供 SPA fallback，因此 Railway、Docker 和本地生产预览都使用同一个端口与同源 Cookie。

Railway 配置使用该 Dockerfile，健康检查指向 `/api/health/live`，挂载 `/data` Volume，并通过环境变量配置管理员密码和模型 provider。Railway 负责 TLS，应用启用代理头支持。Docker Compose 使用同一镜像、同一 `/data` 契约和命名 volume，不再默认启动完整 Langfuse 服务；Langfuse 保持可选 profile。

README 首屏改为真实部署和使用流程：Railway 部署、挂载 Volume、设置环境变量、访问登录页、创建首个岗位。开发说明、备份恢复、升级迁移、反向代理和故障排查分别提供可复制命令。

### 可观测性与运维

提供 `/api/health/live` 与 `/api/health/ready`；前者只表示进程存活，后者检查数据库、数据目录和核心配置。HTTP 请求、后台任务、SSE 与 WebSocket 使用统一 request/task/session ID 和结构化日志，错误日志不得包含简历正文、JD 全文、音频内容或密钥。

后台任务启动后先写数据库；服务重启时将遗留 `pending/running` 任务标为可恢复状态，用户从原任务页显式恢复。Langfuse 继续可选，未配置时核心日志和健康检查仍足够定位部署问题。

## 验收与测试

### 自动化测试

- 后端：认证 Cookie、同源保护、登录限流、项目 CRUD/归档、聚合工作台、服务端所有者约束、迁移旧数据库、统一数据目录、备份恢复、就绪检查与结构化错误。
- 面试：文字 SSE 恢复、重复提交、幂等总结；语音 Cookie 鉴权、权限/设备预检、合成 PCM 轮次、断线恢复、时长上限和项目上下文注入。
- 前端：认证与 401、项目创建、三步派生状态、任务恢复、禁用能力提示、暗色主题和响应式组件测试。
- 端到端：使用仅测试环境可启用的确定性模型适配器，覆盖登录、创建 JD 项目、等待分析、上传简历、完成匹配、文字面试、语音面试与总结回到工作台。
- CI：后端 pytest/ruff、前端单元测试与生产构建、Playwright 核心流程、Docker 镜像构建。

### 发布验收

1. 全新 Railway 实例在绑定 Volume 和设置环境变量后可通过一个公开 HTTPS URL 完成整个主链路。
2. 重启或重新部署不会丢失项目、文件、任务状态、会话事件或总结。
3. 未登录用户不能访问 REST、SSE、WebSocket、上传文件或静态数据路径，也不能通过伪造 `user_id` 读取记录。
4. 文字和语音都能完成至少两轮问答、断线恢复与总结；错误不会留下永久加载状态。
5. 桌面与移动端无溢出、遮挡或不可达操作，明暗主题均通过浏览器视觉检查。
6. 从旧数据库升级后，原有记录可在未归档历史中读取，新项目功能可正常使用。
7. Docker Compose 使用同一镜像和数据目录完成同样流程，备份包可在新实例恢复。

## 明确不在 v1 范围

多用户注册、组织/班级、邀请系统、商业计费、跨实例同步、移动原生应用、在线共享报告和对象存储不进入本次实现。GitHub 分析只做认证、配置诊断和现有功能回归，不重写其分析管线。
